# Agent Note: The model returns facts only; candidate scopes and prices are generated server-side

Status: implemented

## Problem

M3 needed the model to participate in requirement understanding, but the product floor is "the
model must never decide an amount and must never directly produce a payable option". The model is
called through the OpenAI-compatible gateway `api.uselunora.com` as `deepseek-v4.1-flash`. Measured
on this gateway, `response_format` (`json_object` and strict `json_schema`) has no effect: the
parameters are accepted but the model still emits prose or its own JSON schema.

Squeezing "extraction + candidate scopes + evidence" into one nested JSON call leaves the output
shape to the model, so the program can only accept or reject wholesale, with a rejection rate too
high to use (measured: 5 consecutive replies, none matching the agreed schema). Meanwhile the
combination of a candidate scope — how many pages, whether to include an external link, which
capabilities to cut — is inherently a pricing-rules problem, not a language problem.

## Decision

The model does **fact extraction only**, with the port contract fixed at five keys: `pages`,
`budget_usd`, `deadline_days`, `assets_ready`, `features`. `extra="forbid"` — any extra key, type
violation, prose or code fence rejects the reply whole (`422 model_output_invalid`); no speculative
repair.

Candidate scopes are generated by pure functions in `app/ai/candidates.py`: first price "as
briefed"; if infeasible and narrowable, add a "one page + external ordering link + only capabilities
the studio actually offers" option — at most two. Prices and violations are always computed by
`app/rules.evaluate`; the model's `budget_usd` is displayed only as "what the model read" and never
enters a quote.

`app/ai/client.complete_json` is the single adapter (ports-and-adapters): one request, no automatic
retry, 60 s timeout; failures surface to the seller as `502 model_unavailable`, and a human decides
whether to price by hand or retry. Every call (success, rejection, transport error) is written to
`ai_extractions` with model name, prompt version, input message IDs, raw output, parsed result,
error code and latency, as evaluation evidence.

The prompt is pinned at `facts-v6` and follows two measured conclusions: the system prompt must be
short and imperative (persona openers flip flash models into prose); the user message carries only
the plain-text brief, never batched JSON (JSON payloads make the model "rearrange this JSON" instead
of extracting facts). Plain-text brief + five-key schema measured 5/5 at 2.1–3.2 s.

## Alternatives considered

1. **One call returning nested structure (requirement fields + candidate scopes + evidence IDs)**.
   Strongest case: one fewer mapping, the model can attach trade-off reasoning, and the product
   story is more "AI-native". Rejected: measured 0/5 schema compliance on this gateway, and the
   candidate combination is inherently a rules problem; handing rule judgement to a language model
   makes "why this price" impossible to verify mechanically.
2. **Rely on strict `json_schema` to enforce the shape**. Strongest case: server-constrained
   decoding is theoretically the most reliable. Rejected: the gateway accepts the parameter but does
   not enforce it, and the model still emits its own schema; recorded once, not retried.
3. **Accept any JSON and map key names heuristically**. Strongest case: visibly raises the
   "looks successful" ratio. Rejected: key-name mapping is silent correction — it treats the model's
   inventions as facts, violating the single-path and Fail-Fast iron rules.
4. **Automatically retry once on failure**. Strongest case: extraction is read-only, so retrying
   fits idempotency and could double the success rate. Rejected: retries mask model instability
   (the evaluation needs the real failure rate) and double per-click latency and cost; instead the
   failure is surfaced to the seller, who decides between retrying and pricing by hand.

## Consequences

- Benefit: amounts cannot be influenced by the model; candidate combinations are unit-testable;
  changing model versions only requires keeping the five-key contract; every call is traceable to a
  prompt version and raw output.
- Cost: the model no longer contributes "option narrative" — candidate `rationale` is fixed
  server-side copy; `features` arrive as free strings (measured: `online_ordering` did appear), and
  mismatches with capability codes surface through `unsupported_requests` instead of being mapped.
- Known limitation: on this gateway the model still occasionally returns prose; the API returns
  `422` and the UI says plainly "not priced, handle manually" — there is no fallback parser.
- If a future provider truly enforces `json_schema`, handing candidate generation back to the model
  can be re-evaluated; a new note should be written then and linked to this page.

## Verification

- `backend/tests/test_ai_extraction.py`: construction of the two server candidates, amounts from the
  rules, prose/extra keys/out-of-range pages rejected, evidence rows written, `{"extraction": null}`
  when there is no latest draft.
- Manual test on the real gateway: `facts-v6` passed the five-key contract 5 times in a row; one
  full UI call took 2.2 s and produced "As briefed $700 / cannot deliver" and "One-page launch,
  narrowed to fit $500 / deliverable".
