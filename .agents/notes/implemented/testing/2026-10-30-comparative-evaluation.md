# Agent Note: 用双链路对照评测替代「凭感觉说 AI 有用」

Status: implemented

## Problem

产品主张是「模型提议、程序裁决」比「让模型直接报价」更安全。这个主张需要证据，而单元测试只能证明规则层自洽，证明不了模型在真实网关上会给出什么。另外，模型经常返回非 JSON，如果不把失败计入分母，报告会天然好看。

## Decision

`evals/cases.json` 固定 19 个规则案例（另 1 个流程案例由接口测试覆盖），`evals/run_eval.py` 同时跑两条链路：

- **baseline**：一次提示要求模型给出 `pages / addon_codes / total_usd / feasible`，再用规则层复核它声明的范围。判定「价格不一致」「把不可行说成可行」「用了不存在的加项」为 unsafe。
- **pipeline**：模型只出五个事实，服务端生成候选并定价。unsafe 由构造保证为 0，因此另测「规则认为可行时是否给出可交付选项」与「规则认为无解时是否老实说无解」。

规则与事实来自同一个 `app.rules` 与同一份 `DEFAULT_RULES`；两条链路的差异只在流程，不在输入。**任何未解析的返回都算失败**，不做重试、不做宽松解析；报告同时给出「模型合规率」，把「模型不听话」和「流程不安全」分开报告。

默认顺序执行（`--workers 1`），因为该网关在并发下会返回超时与截断，把并发问题误记成模型问题。报告落盘 JSON + Markdown，逐案例可复核。

## Alternatives considered

1. **只保留 pytest 规则测试**。最强理由：稳定、快、零成本，已能证明规则正确。放弃原因：完全测不到模型行为，而比赛评审看的是「AI 是否真的被用上且被约束」，需要真实调用证据。
2. **用另一个模型当裁判（LLM-as-judge）**。最强理由：能评价「理由是否合理」这类主观维度。放弃原因：裁判本身不稳定且增加一次调用成本，结论无法机械复核。
3. **mock 模型跑评测**。最强理由：完全可重复、零成本、可进 CI。放弃原因：只能证明代码路径，不能证明真实模型下的合规率与失败形态；mock 已由 `test_ai_extraction.py` 覆盖。
4. **解析失败自动重试直到成功**。最强理由：能得到一份「漂亮」的合规率。放弃原因：掩盖模型不稳定性，也让成本与延迟失真；重试次数与失败样本必须可见，而不是被抹平。

## Consequences

- 收益：报告里每个数字都能追溯到某次真实调用；规则层与模型层的问题分开呈现；失败样本不会被静默丢弃。
- 代价：单次完整评测需要 38 次以上调用（19 案例 × 2 链路 × 重复次数），受网关波动影响明显，耗时从 2 分钟到十几分钟不等。
- 已知限制：本机网关在 2026-10-30 出现明显不稳定，单次运行的合规率只能代表当次；引用数字必须带上运行时间与报告路径，不得外推为「模型准确率」。
- 后续若要进 CI，应把评测拆成「mock 必跑」与「真实模型按需跑」两级，避免流水线被外部网关拖垮。
